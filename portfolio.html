Field diagnostics

Diagnosing a solar-panel output drop from telemetry

Problem
A solar buoy’s harvest was collapsing over weeks: degradation, weather, or something else?
Approach
Cross-checked the initial read against the actual charge-controller telemetry (battery voltage, current, and charge-state codes) rather than taking the output drop at face value.
Result
The telemetry told two different stories. Most of the drop was the charge controller intentionally curtailing the panel once the battery hit float, confirmed by a full Bulk→Absorption→Float cycle every day, not degradation. A later multi-day total output stop was a separate event, isolated from the curtailment pattern by the state codes never re-entering an active charge state.

Optimization

Energy-aware camera scheduler

Problem
An energy-limited buoy (100 W solar, 1.2 kWh battery) can’t run its 33.7 W camera continuously without draining below a safe floor.
Approach
A hierarchical forecast (7-day planning + 24-hour tuning) feeding a linear-programming scheduler bounded by real battery limits.
Result
The only scheduling policy that never breached the battery safety floor across the deployment, at a sustainable 23% camera duty cycle. Safety came from the constraint structure, not forecast precision.

Scheduler: the safety floor is a hard constraint
# Weekly camera-energy budget: maximize uptime, never breach the battery floor
def solve_weekly_budget(soc0, harvest_7, floor=240, margin=70, cam_w=33.7):
    net  = 0.90 * harvest_7 - 3.0 * 24           # charge eff · hotel load
    cost = -(1.0 + 0.05 * np.arange(6, -1, -1))  # front-load: spend early, not "never"
    A, b = [], []
    for k in range(7):                           # floor must hold on every day
        row = np.zeros(7); row[:k+1] = 1
        A.append(row); b.append(soc0 - floor - margin + net[:k+1].sum())
    return linprog(cost, A_ub=A, b_ub=b, bounds=[(0, 24*cam_w)]*7, method="highs").x

# 24-hour-ahead solar forecast: learns the daily cycle from 72 h of history
class LSTMSolarForecaster(nn.Module):
    def __init__(self, in_dim=4, hid=64, out=24):
        super().__init__()
        self.lstm = nn.LSTM(in_dim, hid, num_layers=2, batch_first=True, dropout=0.1)
        self.head = nn.Linear(hid, out)
    def forward(self, x):            # x: (batch, 72 h lookback, 4 features)
        return self.head(self.lstm(x)[1][0][-1])

In deployment, this runs as a daily loop: read the battery state of charge, pull a fresh 24-hour and 7-day forecast, solve for the day’s camera budget, and push an hourly on/off plan to the buoy, re-planning every morning against what actually happened.

Battery · Measurement

Validating state-of-charge against real cells

Problem
Is battery voltage a trustworthy state-of-charge gauge for the LiFePO₄ pack the buoy relies on?
Approach
Reconstructed state-of-charge by coulomb-counting real current and voltage telemetry (∫ V·I dt), then compared it against the voltage–OCV estimate over the deployment.
Result
Voltage-only SoC drifts ~15% in the flat LiFePO₄ region; recommended coulomb counting for the on-buoy estimator. Confirmed the pack was energy-sustainable (+2 Wh/day net).

Systems tooling · power budgets

Power budgeting & system sizing

Problem
Before any scheduling, each deployment needs its battery and solar array sized to a specific duty profile and site.
Approach
Built a Python Marine System Power Analysis Tool (time-series, phase-aware, component-level modeling with location-specific solar) and compiled full system power budgets.
Result
Battery (7–18 Ah) and solar (30–109 W) sizing across 7 operational profiles for two marine systems (AMEC + IMTA). Reusable framework, later adapted across deployments.
