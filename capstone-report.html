01Implementation: duty cycling as the mechanism for balancing a remote system's power budget

Σ P_i (running) ≤ P_solar,avg
P_i: the draw of system i while it's on (base load, camera, sonar, UV-C light, …) · P_solar,avg: average power the panel is putting in, refilling a fixed battery with no wall outlet behind it. Whenever the sum exceeds the average, not everything can run at once, so each system runs only part of the time: its duty cycle, sized to what the battery can afford.
On this buoy, that general form becomes:
P_base + P_camera + P_sonar + P_uvc = 1.7 + 33.7 + (up to 27) + 6.6 = up to 69 W > 9.6 W = P_solar,avg
That gap is exactly what duty cycling closes.

02Forecasting: current implementation, and the research questions it opens up

Duty cycling alone is reactive, deciding today from today's battery. Forecasting adds a second layer: an estimate of tomorrow, so the system can plan ahead instead of just reacting.

In practice this couples two forecast horizons, an accurate 24-hour model for today's decision and a rougher 1-week model as an early warning, which is what caught the cloudy day above and is the basis for the safety result in Section 05. All of it is trained on just 41 days from the Gulf Coast IMTA buoy, its full deployment before retrieval, so the open research question is what a full multi-season dataset would unlock: real seasonal patterns, forecastable degradation, and a method that transfers to a new site without waiting a year to prove it.

Executive Summary

The Year 1 proposal established a framework for evaluating power and data budgets for marine energy monitoring systems deployed in remote marine environments, focusing on renewable power integration to inform system design. One year later, this investigative question has yielded concrete engineering deliverables: an automated data pipeline, a robust optimization framework, a comparative benchmarking study of solar forecasting models, and a novel hardware diagnostic methodology. The diagnostic method successfully distinguishes genuine hardware faults from nominal, edge-case system behavior, and has been empirically validated across two independent deployments.

03 Optimization Framework and Power Sizing

Three optimization approaches were developed at different horizons; the approach selected as realistic for actual deployment is indicated below:

ApproachHorizonDecisionUse case
Integer LP (CVXPY / GLPK_MI)48 hoursBinary on/offMaximize uptime window
Proportional allocationDailyContinuous duty %Sustainable deployment (current default)
Seasonal modelWeek+Estimated solarLong-term planning

The proportional allocator reads battery state of charge from voltage, retrieves a solar forecast, and reallocates duty cycle by priority on a daily basis: base load remains continuously active, while camera duty is scaled to available power rather than following a fixed schedule.

How the daily allocation is derived

Each morning, the day's usable power budget is the forecast solar plus whatever battery headroom sits above the safety floor, both spread over 24 hours:

P_avail = E_solar,fcst / 24 + (SoC(t) − SoC_floor) / 24
E_solar,fcst: forecast solar yield for the day (Wh), from LSTM or the joint policy · SoC_floor: the 20% safety floor (240 Wh on this buoy's 1200 Wh battery) · dividing by 24 turns both terms into an average hourly budget, not a one-shot allowance.

That budget then gets handed out by priority, highest weight first, each system capped at what it actually draws:

duty_i = clip( (P_avail − Σ_{j<i} w_j · D_j) / D_i, 0, 1 )
w_i: priority weight (base load 1.0, camera 0.9) · D_i : rated draw (1.7 W base, 33.7 W camera) · base load is served in full first since it's always-on and cheap; the camera's duty cycle absorbs whatever's left, clipped to the 0–100% range it can physically run.

The 48-hour integer LP variant swaps that daily heuristic for an explicit optimization: maximize on-hours subject to the battery never leaving its safe range:

maximize Σ_t x_t subject to SoC_{t+1} = SoC_t + (P_solar,t − P_base − x_t·P_cam)·Δt / C_batt SoC_min ≤ SoC_t ≤ SoC_max for all t x_t ∈ {0, 1}
x_t: binary camera on/off decision each hour · C_batt: 1200 Wh capacity · solved with CVXPY's GLPK_MI branch-and-bound solver. This is what actually enforces the battery floor: the proportional allocator approximates it daily, the LP guarantees it hour by hour, which is why the safety result in Section 05 holds regardless of which forecaster feeds it.

The code behind both formulas

The proportional allocator and the LP scheduler are each a small amount of code. The allocator is the daily heuristic from Section 03, applied in priority order:

proportional allocation, run once per morning
# P_avail in watts, averaged over the next 24h
p_avail = e_solar_fcst / 24 + (soc_now - soc_floor) / 24

duty = {}
remaining = p_avail
for system in sorted(systems, key=lambda s: -s.priority):
    duty[system] = min(max(remaining / system.draw_w, 0), 1)
    remaining -= duty[system] * system.draw_w

# duty["camera"] ≈ 0.23 on an average day, matching the worked example above

The 48-hour variant swaps that heuristic for an actual solve, camera on/off each hour, subject to the battery never leaving its safe range:

48-hour integer LP, cvxpy + GLPK_MI
import cvxpy as cp

x = cp.Variable(48, boolean=True)          # camera on/off, one var per hour
soc = cp.Variable(49)                        # battery state of charge, Wh

constraints = [soc[0] == soc_now]
for t in range(48):
    constraints += [
        soc[t+1] == soc[t] + (p_solar[t] - p_base - x[t]*p_cam) * dt,
        soc[t+1] >= soc_min,
        soc[t+1] <= soc_max,
    ]

problem = cp.Problem(cp.Maximize(cp.sum(x)), constraints)
problem.solve(solver=cp.GLPK_MI)

A day in practice: what 23% duty cycle looks like

Applying measured figures to the daily allocation formula: average solar generation on this buoy is approximately 9.6 W hourly (230 Wh over 24 hours). Base load accounts for 1.7 W, leaving (9.6 − 1.7) / 33.7 = 23% of the day available to the camera, approximately 5.5 hours rather than continuous operation. The scheduler does not distribute those hours evenly: it front-loads camera operation while the battery is at capacity and tapers off as the day's solar income diminishes.

Operational Deployment Workflow

The procedure below outlines how an engineering team at MarineSitu would apply this framework to a new deployment, from initial planning through day-to-day operation:

  1. Catalog the payloads. Document every device entering the water or mounted on the buoy, along with its rated draw and operational priority. This inventory constitutes the D_i and w_i terms in the Section 03 formula.
  2. Size the battery and panel against the budget. Apply the daily allocation formula in reverse: given the payload inventory and required daily operating hours for each device, derive the battery capacity and solar panel size necessary to satisfy the budget before hardware procurement.
  3. Deploy and initiate logging. Establish continuous telemetry, panel output, battery voltage, and charge-controller state, from the first day of deployment. Section 02 documents the pipeline this logging feeds into.
  4. Execute the daily operational loop. Each morning: read battery state of charge, retrieve the solar forecast (Section 04), run the allocator (Section 03), and transmit the resulting duty cycles to the buoy.
  5. Monitor for pattern, not just magnitude. When harvest readings appear anomalous, verify against weather conditions and the charge controller's own state codes before concluding hardware failure has occurred. Section 06 documents this verification process applied twice, across two independent sites.
  6. Feed validated data back into the forecaster. As telemetry accumulates, retrain on the clean window (Section 07 defines the data-quality criteria applied here) so forecast accuracy continues to improve rather than degrading on outdated assumptions.

04 Solar Forecasting Models

Eleven models were benchmarked against the verified 41-day dataset using a proper 28-day train / 7-day test split (an earlier version of this benchmark permitted test data to leak into training, which is why the naive baselines had shown an impossible 0.0 W error; this discrepancy prompted a full review of the evaluation methodology, documented below).

Evaluation Metrics: MAE and RMSE

Every model evaluated performs the same task: analyze the preceding 24 hours of panel output and predict the subsequent hour. Mean absolute error (MAE) is the average magnitude of that prediction's deviation, in watts, regardless of direction. An MAE of 0.93 W indicates the model was typically inaccurate by under a watt. Root mean squared error (RMSE) evaluates the same deviation but squares each error before averaging, so a small number of large errors increases RMSE disproportionately relative to many small ones. When a model's RMSE is substantially higher than its MAE relative to its peers, this indicates the model is not consistently slightly inaccurate; rather, it performs adequately most of the time and fails significantly on occasion. Lower values are preferable for both metrics, and this is the basis of the benchmark: the model that most closely approximates actual panel output, most consistently, is the superior model.

LSTM outperforms Prophet by approximately 4× on this dataset, and the underlying cause is more significant than the figure itself: the dataset spans only 41 days, intra-day volatility is high, and no weather input is available. A 24-hour lookback window that tracks the panel's own recent behavior outperforms a model designed to assume smooth seasonal trends. In practice, this indicates LSTM is appropriate for hour-to-hour scheduling, while Prophet (or a joint policy) is better suited to the 7-day energy budget.

Satellite Irradiance as a Predictive Input

This analysis evaluated whether ERA5 irradiance data improves daily-harvest prediction accuracy. Historical irradiance data alone produced no improvement (114 Wh MAE vs. 113 Wh geometry-only), as the model has no visibility into the days it is predicting. Incorporating future irradiance (an oracle input, not a genuine forecast) reduced error to 96 Wh, an improvement of approximately 15%, and predictions tracked solar conditions rather than remaining flat. Operational deployment would require an actual weather forecast rather than an oracle input; accordingly, this result represents a best-case upper bound rather than a deployment-ready result.

Key finding

Forecast precision determines footage yield, not operational safety. A forecaster five times less accurate than LSTM still produced zero floor violations once paired with a long-range outlook and a hard LP constraint. Safety is attributable to the LP floor plus margin, independent of which model is generating the prediction. Over the June 16 to 22 test window, the joint scheduler delivered 31 hours of footage with zero violations, and battery charge never fell below 382 Wh against a 240 Wh floor.

06 Hardware Validation and Deployment Audits

The final stage of this work subjected all preceding analysis to validation against physical deployment conditions, and identified that one prior conclusion required correction.

Site 1: Gulf Coast IMTA Buoy

The initial analysis of this buoy's telemetry indicated panel output trailing the weather-expected curve by approximately 60% beginning June 4, attributed to fouling or panel degradation, which formed the basis for an early "panel health outweighs forecast accuracy" hypothesis. Verification against the charge controller's own state codes, rather than inference from satellite irradiance alone, does not support that hypothesis: the battery reaches full charge daily and the controller deliberately reduces output, a textbook Bulk → Absorption → Float cycle. This is not indicative of degradation.

This same verification pass identified a condition the original analysis had missed entirely: from June 25 through July 2, the charging path remained in an Off state for 100% of readings across eight consecutive days, with no charging activity and no fault code logged. This pattern is inconsistent with solar variation regardless of underlying cause, and the timing correlates closely with the buoy's July retrieval, making equipment removal the leading candidate explanation over an active fault, though this remains unconfirmed. In either case, this window was present, uncorrected, in the training data for both forecasting baselines, precisely at the point in the series from which the LSTM model seeds its forecast.

Site 2: Hawaii Island

A second, independent deployment was evaluated using the same charge-controller state model, different hardware, with no assumptions carried over from Site 1 apart from the methodology itself. Daily harvest remained flat at 180 to 240 Wh/day regardless of cloud cover ranging from 26% to 93%, the same weather-decoupled signature identified as curtailment at Site 1. This finding was confirmed directly by the site's hardware contact: the system is oversized relative to its load, resulting in a float state on most days regardless of conditions. The methodology transferred successfully on first application.

A separate two-day power collapse at this site was determined to have a distinct cause. A wind-speed increase correlated with the timing of the collapse in a side-by-side chart comparison, was flagged as a candidate explanation, and was subsequently confirmed: the solar panel had physically detached from its mount during high wind conditions. This is a mechanical failure rather than an electrical one, representing a materially simpler remediation than the alternative explanations under consideration.

07 Root-Cause Debugging Analysis

Independent of the interpretive corrections documented in Section 06, several discrete code and data defects were identified during this work, each of a category that remains undetected until a computed value is validated against the physical system it is intended to represent.

  • Data leakage in the model benchmark. Symptom: the naive seasonal and naive drift baselines reported an implausible 0.0 W MAE. Cause: the training and test windows overlapped, such that the "next hour" value the naive model predicted was already present within its own training data. Fix: the benchmark was rebuilt using a strict 28-day train / 7-day test split. The corrected results are presented in Section 04.
  • Yield counter resets during deployment. Symptom: daily energy totals exhibited implausible negative values on certain days. Cause: the calculation relied on the charge controller's cumulative yield_wh counter, which resets without notice whenever the controller recalibrates, producing negative values when differenced. Fix: instantaneous panel_w readings are now integrated over time rather than derived by differencing the counter.
  • Forecast model trained on a fault window. Symptom: LSTM predictions exhibited a systematic low bias at the point of greatest operational relevance. Cause: the 8-day Gulf Coast outage (Section 06) remained, uncorrected, at the tail of the training series and was being interpreted as genuine solar variation, precisely where the model seeds its subsequent forecast. Fix: all data following June 25 is now explicitly excluded from training.
  • Undetected lookback window misconfiguration. Identified during remediation of the preceding defect. Cause: raw telemetry is logged at per-minute resolution, but lookback=24 in the forecasting code had been implemented under the assumption of 24 hourly steps, such that the model was effectively observing only 24 minutes of history rather than 24 hours. Fix: data is now resampled to hourly resolution prior to constructing input sequences.
  • Power draw value mislabeled. Symptom: the optimizer was systematically under-allocating power to non-camera systems. Cause: a value carried forward under the label "camera draw" in fact represented total system draw, comprising base load, the underwater camera, and the surviving topside camera combined, an assumption originating from an early hardware review that had not been subsequently re-verified. Fix: this value was corrected across the optimizer, the input-validation script, the modeling notebook, and a portfolio document, five files in total, all attributable to a single erroneous figure.

08 Potential Next Steps

  • Root cause of the Gulf Coast outage: eight days in a stuck Off state with no fault code logged. The leading candidate explanation is the buoy's July retrieval, which correlates closely with the timing; a decommissioned unit would produce an identical signature, stuck Off with no logged event. This remains unconfirmed pending an actual retrieval date and time; telemetry alone cannot establish causation.
  • Hawaii Island's actual usable battery capacity: the 512 Wh nameplate rating assumes intact safety electronics that were bypassed following a prior, unrelated failure. Actual usable capacity must be derived from underlying cell specifications before it can be applied to any safe-floor calculation.
  • Forecast retraining on the corrected Gulf Coast dataset: both baselines were previously trained through the outage window as though it represented genuine solar variation. Exclusion of this window and re-benchmarking is currently in progress.
